## 1. Goal and exit criteria

fast-proxy does what the roadmap promised: routing by host and prefix, live configuration, load balancing and
health, TLS and ACME, maintenance, authentication and audit, sampling. What it does not do yet is **defend itself**
or **promise anything** to the people who run it.

- **No defense against abusive clients.** There is no client rate limit and no connection limit. A client can open
  as many connections as the file-descriptor limit allows, and send a request body as slowly as it likes. A large
  body is forwarded as it comes, with no size cap. The only request-side limits are two constants in
  `crates/fast-proxy-dataplane/src/server.rs`: a 10 s header-read timeout and a 64 KiB buffered head. On TLS there is
  also the handshake timeout and the handshake concurrency cap (M3), and on HTTP/2 the stream and header-list limits
  with the rapid-reset caps.
- **No published performance numbers, no soak test, no fuzzing, no dependency audit.** The numbers in
  [benchmarks.md](benchmarks.md) come from one laptop. The proxy has never run for more than minutes at a time, its
  parsers and validators have never been fuzzed, and CI checks no advisory database.
- **Thin operator documentation and packaging.** The README is the operator's only manual. There is no container
  image, and no stated promise about what a 1.0 upgrade keeps working.

M7 closes those gaps and ends with the **1.0.0 release**.

**Exit criteria** (from the roadmap, made measurable):

1. **Rate limits work and are live.** A policy on a subsystem or a route (rate, burst, key) answers over-limit
   requests with `429` and `Retry-After` and never forwards them. Admitted traffic stays within 5% of the
   configured rate over 10 s. Policies change through the admin API, UI and CLI without a dropped connection, are
   audited, and reach other instances through the sync poll. The ACME challenge path is never limited. The key table's
   memory is bounded: 1,000,000 distinct client addresses do not grow it past its configured capacity.
2. **Connection limits hold.** With a process-wide and a per-client connection cap, a client that opens connections
   past its cap is refused at accept, without a TLS handshake, while other clients keep connecting and are served.
   An endpoint with a connection cap never has more open requests than the cap; the excess goes to another endpoint,
   or gets `503` when none has room.
3. **Slow clients cannot hold the proxy.** 2,000 connections that trickle headers, trickle a body, or read the
   response slowly are closed within their timeouts. Meanwhile a normal client's p99 latency stays within 2x its
   value without the attack, and no request fails.
4. **Size limits refuse cleanly.** Too many or too large headers get `431`, a request target that is too long gets
   `414`, and a body over its route's cap gets `413`. A cap the `Content-Length` already exceeds is refused before a
   byte reaches the upstream; a streamed body that crosses its cap is cut and counted. A request carrying both
   `Content-Length` and `Transfer-Encoding` is never forwarded with both.
5. **It runs for a day.** A 24-hour soak runs steady load, a reload every minute, endpoints flapping, certificate
   writes and sampling on. After a one-hour warm-up resident memory grows by less than 5%, open file descriptors
   return to their idle count, and no request fails apart from the injected faults. A 30-minute version runs
   nightly in CI.
6. **Benchmarks are published.** [benchmarks.md](benchmarks.md) holds numbers from a documented Linux machine,
   generated by a script anyone can rerun. They cover plain HTTP, HTTPS h1 and h2, handshakes, and limits on and off.
   They are compared with the M6 baseline, and informationally with nginx on the same machine. With limits on at
   their defaults, throughput stays within 3% of limits off.
7. **Fuzzing finds nothing.** Every target in section 5.4 runs at least one CPU hour without a crash or a timeout
   before 1.0. Each runs for 60 s on every pull request, and longer every night.
8. **The 1.0 security review is done.** `docs/security-review-1.0.md` covers the whole system against a written threat
   model: admin plane exposure, ACME and certificate key storage, header trust and request smuggling, denial of
   service, the supply chain and file permissions. It leaves no open high or medium finding. `cargo deny` (advisories,
   licenses, bans, sources) is a CI gate.
9. **An operator can run it from the docs alone.** There is an operator guide, a configuration reference that a test
   proves covers every `config.toml` key, and an admin API reference that a test proves covers every registered
   route. The systemd and Docker recipes are built and checked in CI.
10. **It is packaged.** Every release publishes a multi-arch (amd64, arm64) container image to GHCR, runs as non-root
    with a volume for state, and carries a health check. Static Linux binaries (musl, amd64 and arm64) join the four
    existing targets, with checksums, an SBOM and build provenance.
11. **Upgrades keep data.** A database written by every released version since v0.1.1 opens with the 1.0 binary and
    migrates with its configuration, certificates, tokens and samples intact (the owner's rule of 2026-11-16, AGENTS.md
    "Compatibility and migration"). A CI job proves it with the real old binaries.
12. **No regression.** The M1 to M6 and M4 exit criteria still pass. The data plane still loads the snapshot once per
    request and never touches the database. Metric labels still come only from configuration names.

## 2. Scope

### In scope

- A new pure crate, `fast-proxy-limits`: the rate-limit algorithm, the bounded key table, per-client connection
  counting, and the limit types and defaults. The token bucket in `fast-proxy-sampling` (`bucket.rs`) moves here so
  there is one implementation.
- Rate-limit policies as configuration (model, schema with a migration, compile into the snapshot, the admin API,
  CLI and UI).
- Connection-level defenses in the data plane: connection caps, timeouts for idle connections, slow bodies and slow
  readers, size limits, and smuggling checks. Per-endpoint connection caps in `fast-proxy-balancing`.
- The schema migration mechanism, if the M4 stack does not land it first (carry-over C1).
- Fuzzing (`cargo-fuzz` targets, CI jobs), `cargo deny`, the soak and load harness, published benchmarks, and the
  tuning they point to.
- The 1.0 security review and its fixes.
- The operator guide, configuration and API references, deployment recipes, `SECURITY.md`, `CHANGELOG.md`.
- The container image, more release targets, SBOM and provenance, the upgrade test, and the 1.0.0 release.

### Out of scope (later, or never)

| Item | Where |
|---|---|
| A cluster-wide rate limit (one shared budget across instances) | post-1.0; limits are per instance (L4), as the sampler's are |
| Rate limiting on request attributes beyond the client address and one header (path patterns, JWT claims, expressions) | post-1.0; a policy on a route covers paths |
| Request queueing (holding over-limit requests instead of refusing them) | not planned; `429` with `Retry-After` is the contract |
| A web application firewall, bot detection, IP reputation lists | never in the core |
| Static allow and deny lists of client CIDRs | post-1.0 candidate (small, but not needed for 1.0) |
| HTTP/3, DNS-01, TLS-ALPN-01, ARI, service discovery | post-1.0 candidates in the ROADMAP; M4's X1 and X2 stay there |
| Kubernetes manifests or a Helm chart | post-1.0; the container recipe is the base |
| Package-manager packages (deb, rpm, Homebrew) | post-1.0 |
| A versioned admin API path (`/api/v1`) | decided in L12: no new prefix; the 1.0 promise covers `/api` as it is |

## 3. Design decisions for M7

All accepted by the owner on 2026-11-16.

| # | Decision | Recommendation |
|---|---|---|
| L1 | Where each limit lives | **Process settings** (restart to change) in a new `[limits]` section of `config.toml`: connection caps, the connection-level timeouts, the header and URI limits, the rate-limit table's capacity, and the default body cap. These protect the process, so they belong with the listeners. **Live configuration** in the database: rate-limit policies, per-route body caps, per-group endpoint connection caps. They describe traffic per subsystem and route, so they live beside the routes. Rate-limit policies **are `Config`**: a revision holds them and a rollback restores them, like routes. This differs from sampling settings (J3) because a rolled-back route should come back with its limits. **Accepted.** |
| L2 | The rate-limit algorithm | **GCRA** (the generic cell rate algorithm, equivalent to a token bucket): one `AtomicU64` per key holds the theoretical arrival time, updated with one compare-and-swap. It needs no refill timer and no lock, and gives an exact `Retry-After`. Its key property for L3: a key whose stored time is in the past is the same as a fresh key, so idle entries can be evicted without changing any answer. The sampler's token bucket moves into `fast-proxy-limits` with its late-arrival rule, and keeps its behavior. **Accepted.** |
| L3 | The key table (bounded memory) | Sharded (64 shards, each a small `HashMap` behind a mutex held for one lookup), with a total capacity from `[limits] rate_limit_keys` (default 100,000). A key is stored as a 64-bit hash with a per-process random seed, never the address itself. When a shard is full it **evicts entries whose time has passed**, which by L2 changes no answer. If none has passed, the request is **admitted (fail open)** and counted as `rate_limit_table_full`. A collision-merged table (as M6 J6) is rejected because it would limit innocent clients. Fail-open is preferred because an attacker who fills the table would otherwise turn it into denial of service for everyone. **Accepted.** |
| L4 | Per instance, not per cluster | Each instance keeps its own table, as the sampler's limits do (M6 J11, J18). With N instances behind a balancer, the effective limit is up to N times the policy. The UI, API and docs say "per instance" next to the number. A shared budget would put the database on the request path, which is against the architecture rules. **Accepted.** |
| L5 | Rate-limit keys | `client` (the **effective** client address: `X-Forwarded-For` counts only from `trusted_proxies`, as maintenance bypass does), or `header:<name>` (the value of one request header, hashed, never stored, logged or sampled raw, and falling back to the client address when the header is missing). The header key exists for APIs keyed by an API token. The header named in the policy is added to the redaction list automatically. IPv6 clients are keyed by their /64 by default (`ipv6_prefix`, 48 to 128), so one host cannot rotate addresses inside its own prefix. **Accepted.** |
| L6 | Where the check runs | After the host and route matched, **after the ACME challenge, the redirect, the 421 rule and maintenance**, before an endpoint is selected. A maintenance answer and a redirect cost nothing upstream and need no limit. The challenge must never be limited (M4 touch point), and running the check after it guarantees that. A route policy replaces the subsystem's policy for that route (it does not stack), so one request takes one table lookup. The `429` is a fixed proxy response (`responses.rs`) with `Retry-After` in whole seconds, rounded up. The draft `RateLimit` and `RateLimit-Policy` headers are **not** sent in 1.0, because the draft is still changing. **Accepted.** |
| L7 | Connection caps | `[limits] max_connections` (default 10,000, across all listeners, upgraded tunnels included) and `max_connections_per_client` (default 256, by **peer** address, because nothing in the request is known at accept). Both are checked **at accept, before the TLS handshake**: a connection over a cap is closed at once and counted by `reason`. At the global cap the accept loop also waits 10 ms per refusal so it does not spin. Behind a load balancer every peer is the balancer, so the per-client cap can be set to `0` (off), and the docs say so. **Accepted.** |
| L8 | Endpoint connection caps | `max_requests` on an upstream group (default unset, meaning unlimited), counted with the in-flight counter `EndpointRuntime` already keeps. An endpoint at its cap is **ineligible** for selection, like a draining one, and the balancer moves to the next. When every eligible endpoint is at its cap the request gets `503` with reason `endpoint_capacity`, never a queue. A retry respects caps too. No change to the "draining and disabled are never selected" rule; panic mode (M2) does not override a cap. **Accepted.** |
| L9 | Timeouts against slow clients | The existing `header_read_timeout` (10 s) and HTTP/2 limits become `[limits]` keys with the same defaults. New: `idle_timeout` (60 s, a keep-alive connection with no request in flight is closed), `body_read_timeout` (30 s with no progress on a request body: the request is cancelled, `408` if the response has not started, counted), and `send_timeout` (60 s with no progress writing to a client, the connection is closed). The last two are implemented as a `ProgressIo` wrapper around the client stream that records the last read and write instant. One timer per connection checks it, so there is no per-chunk allocation. Spike G2 confirms the wrapper's cost and which of these hyper's own `header_read_timeout` already covers between keep-alive requests. Upgraded tunnels get `tunnel_idle_timeout` (1 h, off with `0s`). **Accepted.** |
| L10 | Size limits | `[limits] max_header_count` (100), `max_header_bytes` (the existing 64 KiB head buffer), `max_uri_bytes` (8 KiB), refused with `431` and `414` as fixed responses. `max_body_bytes` is a process default (default **unlimited**, so 1.0 changes no existing upload) with a per-route override in the database. A known `Content-Length` over the cap is refused with `413` before the upstream is contacted; a streamed body that crosses the cap is cut, the upstream request aborted, and the client gets `413` if no response started. These numbers are the same table as the M6 J7 "unusual headers" thresholds, so a request is refused or sampled by one rule set (the M6 touch point). **Accepted.** |
| L11 | Request smuggling | Refuse with `400` (fixed response, counted) a request with both `Content-Length` and `Transfer-Encoding`, with more than one `Content-Length`, with a `Transfer-Encoding` other than a final `chunked`, or with a header name or value that HTTP/1.1 forbids, before anything is forwarded. For HTTP/2 requests forwarded as HTTP/1.1, refuse connection-specific headers and any `\r` or `\n` in values (hyper's h2 server rejects most of these; the review and Q-tests check the remainder). The forwarded request never carries both framing headers. These checks are pure functions in `headers.rs` with unit and fuzz coverage. |
| L12 | What 1.0 promises | A short `docs/stability.md`, effective from 1.0.0. **Kept across 1.x:** `config.toml` keys (deprecated keys still parsed and warned about for all of 1.x), the admin REST API under `/api` (fields may be added, never removed or renamed), the CLI's commands, flags and exit codes, metric names and labels, the access log line format, and **every database written by 1.x opening in later 1.x** with its migrations. **Not promised:** the UI's look and layout, log message text, `/api` endpoints marked experimental. This extends the owner's schema rule to the other public surfaces from 1.0 on. Until 1.0.0 is tagged, the "no compatibility work" rule in AGENTS.md still applies to config, API and behavior. **Accepted.** |
| L13 | Fuzzing tooling | `cargo-fuzz` (libFuzzer, nightly Rust, Linux CI only) in a `fuzz/` crate outside the workspace, so stable builds, `cargo test` and Windows are untouched. Targets call pure functions only (section 5.4), and a seed corpus is checked in. Each target runs for 60 s per pull request and 20 minutes nightly, and any crash input is committed as a regression test. `proptest` stays for properties. **Accepted.** |
| L14 | Supply-chain gate | `cargo deny check` in CI (advisories from RustSec, an allow-list of licenses, a ban on duplicate major versions of `tokio`, `hyper`, `rustls`, crates only from crates.io). `unsafe_code = "forbid"` as a workspace lint every crate opts into (none uses `unsafe` today; a lint also covers tests, examples and build scripts), checked by a test over the manifests, as the store's "no crypto dependency" check is. GitHub actions stay pinned by SHA. |
| L15 | The container image | A multi-stage build: compile `x86_64-` and `aarch64-unknown-linux-musl` statically (rustls and bundled SQLite need no system library), then copy into `gcr.io/distroless/static:nonroot` (no shell, user 65532). `/var/lib/fast-proxy` is the volume for the database and the master key, the default config points there, ports 8000, 8443 and 9000 are exposed, and the image health check runs `fast-proxy status --local` (a new flag that calls `/api/health` with no token). The admin plane stays on loopback by default; the recipe shows admin TLS for exposing it. Published to `ghcr.io/prasenjit-net/fast-proxy:<version>` and `:latest` by the release workflow, signed with keyless cosign, with an SBOM (`cargo cyclonedx`) and GitHub build provenance. **Accepted.** |
| L16 | Benchmarks, published | A `scripts/bench.sh` that starts the backend and the proxy, runs `oha` through a fixed matrix, and writes a Markdown table. The published run uses a named Linux machine (cloud instance type, kernel, CPU pinning for proxy, backend and load generator), three rounds, median reported. nginx is configured equivalently (keep-alive upstream, access log off and on) as a **reference point, not a race**: the doc says what differs. The macOS numbers stay as history. |
| L17 | Soak | `tests/soak/` holds a binary (`cargo run --release --example soak -- --duration 24h`) that drives the real proxy: steady keep-alive load, one config write per minute, one endpoint killed and revived every five minutes, a certificate write per hour, sampling on, and it samples the proxy's RSS and open descriptors every 30 s into a CSV. It fails on any client error outside an injected fault window, RSS growth over 5% after the first hour, or descriptors not returning to idle. Not part of `cargo test`. A nightly workflow runs 30 minutes, and the 24-hour run is done by hand before 1.0 and its graph goes in `benchmarks.md`. |
| L18 | Schema migrations | A `migrations/` module in `fast-proxy-store`: one SQL step per version (`v<N>_<topic>.sql`) that upgrades N-1 to N; all missing steps and the new `user_version` run in one `IMMEDIATE` transaction at open, with the version read again under the lock (several instances may start at once), after a copy of the file (`<db>.pre-v<N>-<unix ms>.bak`, mode 0600, the newest 3 kept, none younger than an hour removed) so the previous release can be restored by hand. `schema.sql` stays the schema of a **new** database at the latest version, with added columns at the end of their tables, and a test proves a new database and one upgraded from schema 5 have the same shape (columns, keys, indexes, `CHECK` clauses). A database newer than the binary is refused (no downgrade). Another instance on the same file with an older binary refuses to open it (the `user_version` check already does), and the docs say to upgrade every instance together. **Accepted** (the owner's rule of 2026-11-16; [ADR 0028](adr/0028-schema-migrations.md)); built as task C1. |

## 4. Target architecture

### 4.1 One request, in order (new steps in bold)

1. **Accept: global and per-client connection caps (L7)**, then the TLS handshake (M3 limits).
2. **Head read: header count, header bytes and URI length (L10), within `header_read_timeout`.**
3. **Framing checks (L11).**
4. Host match, then route match (M1).
5. ACME challenge, redirect, 421, maintenance (M4, M3, M5), unchanged.
6. **Rate limit (L2 to L6): one lookup in the table of the policy that applies; `429` if over.**
7. **Body cap from `Content-Length` (L10): `413` before any upstream work.**
8. Endpoint selection (M2), **skipping endpoints at their `max_requests` (L8)**.
9. Forward, retry (M2). **The body counter and `body_read_timeout` run as the body streams; `send_timeout` while the
   response is written.**
10. Access log, metrics, sampling (M1, M6). Refusals are logged and counted like every other response, and the
    sampler sees them as 4xx (`client_errors`) as M6 section 11 expected.

### 4.2 State across a configuration swap

Rate-limit tables are **keyed by policy identity** (subsystem name, plus the route prefix for a route policy) and
carried across snapshot swaps the way endpoint runtime state is (ADR 0005). A reload therefore does not reset a
client's budget, and a policy whose rate changed applies the new rate from the next request. A removed policy's table
is dropped at the swap. The connection counters belong to the listener, not the snapshot, and are never reset.

### 4.3 Crates and dependencies

```
model ──► limits ──► routing ──► dataplane
            ▲           ▲
            │           └── balancing (max_requests eligibility)
sampling ───┘ (its token bucket moves into limits)
```

`fast-proxy-limits` depends on `model` only and does no I/O; time is a parameter. `sampling` depends on it for the
bucket. `routing` compiles policies into the snapshot and carries the tables. `dataplane` calls it. The data plane
still does not depend on `store`.

## 5. Configuration and data model changes

### 5.1 `config.toml`

```toml
[limits]
max_connections = 10000
max_connections_per_client = 256   # 0 turns it off (behind a load balancer)
header_read_timeout = "10s"
idle_timeout = "60s"
body_read_timeout = "30s"
send_timeout = "60s"
tunnel_idle_timeout = "1h"         # "0s" turns it off
max_header_count = 100
max_header_bytes = 65536
max_uri_bytes = 8192
max_body_bytes = 0                 # 0: unlimited; routes may set their own
rate_limit_keys = 100000
```

The HTTP/2 limits stay in `[data_plane.tls]`, where M3 put them. `--max-connections` overrides the first key on the
command line. Validation refuses a zero timeout where zero means nothing sensible, and a `max_header_bytes` below
4 KiB.

### 5.2 Database (schema 6 to 7, **additive, with a migration**)

New table, plus two nullable columns. A migration step creates them, and the test of L18 compares the result with a
fresh database.

```sql
CREATE TABLE rate_limit_policy (
  id            INTEGER PRIMARY KEY,
  subsystem_id  INTEGER NOT NULL REFERENCES subsystem(id) ON DELETE CASCADE,
  route_id      INTEGER REFERENCES route(id) ON DELETE CASCADE,  -- NULL: the subsystem's policy
  rate          INTEGER NOT NULL,      -- requests per `per_secs`
  per_secs      INTEGER NOT NULL,
  burst         INTEGER NOT NULL,
  key_kind      TEXT    NOT NULL,      -- 'client' | 'header'
  key_header    TEXT,                  -- set when key_kind = 'header'
  ipv6_prefix   INTEGER NOT NULL DEFAULT 64,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  UNIQUE (subsystem_id, route_id)
);

ALTER TABLE route          ADD COLUMN max_body_bytes INTEGER;  -- NULL: the process default
ALTER TABLE upstream_group ADD COLUMN max_requests   INTEGER;  -- NULL: unlimited per endpoint
```

The table and column names follow the schema as it stands when PR2 starts; check `schema.sql` then. Policies
are part of `Config` and of every revision (L1), so rollback restores them, and the revision encoding gains them.

### 5.3 Admin API (sketch)

| Method and path | Access | What |
|---|---|---|
| `GET /api/subsystems/{id}/rate-limit` | `Read` | the subsystem policy, or 404 |
| `PUT /api/subsystems/{id}/rate-limit` | `Write` | set it (audited `rate_limit.set`) |
| `DELETE /api/subsystems/{id}/rate-limit` | `Write` | remove it (`rate_limit.clear`) |
| `GET/PUT/DELETE /api/subsystems/{id}/routes/{routeId}/rate-limit` | as above | the route's policy |
| route and group bodies | as today | gain `maxBodyBytes` and `maxRequests` |
| `GET /api/limits` | `Read` | the process limits in force, the table fill, refusal counters |

Every route is registered in `RouteTable` with its `Access`; the permission-table test enumerates them. The paths
are a sketch: match the existing nesting in `api/routes.rs` when building A1.

  *Result (2026-11-16, hyper 1.11, `header_read_timeout` 1 s):* (a) a keep-alive connection idle between requests
  **is** closed after `header_read_timeout`; a connection that never sends a byte, a body that stalls after its head,
  and a client that never reads a large response are **never** closed. So `idle_timeout` is dropped (the header
  timeout already bounds keep-alive idle) and PR4 adds a first-byte deadline, a per-chunk body timeout and a
  send-stall timeout. (c) `max_headers` answers 431 (default 100); setting another value moves hyper's header buffer

  `Transfer-Encoding`, `Transfer-Encoding` on HTTP/1.0 and two different `Content-Length`s with 400, and drops

## 8. Performance and cost budget

- **Limits on at their defaults, no policy:** within 1% of the M6 numbers (connection counters at accept, a few
  integer comparisons per head, the `ProgressIo` bookkeeping).
- **A rate-limit policy on the route:** within 3% (one hash, one shard lock, one compare-and-swap), at 1 and at 1,000
  distinct clients.
- **Key table memory:** at most about 64 bytes per key times `rate_limit_keys`, so 6.4 MiB at the default. Record the
  measured figure.
- **Slow-client attack:** 2,000 slow connections cost their descriptors and small buffers, with no task spinning.
  Record memory per held connection.
- **Reload:** compiling policies adds to the M5 reload figure only in proportion to the number of policies.
- **The soak** sets the steady-state memory figure for the operator guide's sizing section.

## 9. Risks specific to M7

| Risk | Mitigation |
|---|---|
| **Limits hurting legitimate traffic** (a shared NAT or a load balancer looking like one client) | Body cap unlimited by default; no rate policy unless an operator sets one; per-client connection cap switchable off; the effective client address through `trusted_proxies`; IPv6 /64 keying configurable; every refusal counted by reason and visible in the UI; the docs explain each |
| **The key table as an attack surface** (filling it, hash flooding) | Seeded hashing; capacity from config; eviction of passed entries (L2, L3); fail open with a counter rather than fail closed; P2 floods it in a test |
| **A timeout breaking long-lived traffic** (large uploads, slow APIs, WebSockets) | Timeouts measure *no progress*, not total time; tunnels have their own idle timeout that can be switched off; defaults generous and documented |
| **Body cap interacting with retries and replays** | A cut body is never replayable (ADR 0008 rule extended); tested with retries on |
| **Per-instance limits misunderstood** | "per instance" next to every rate in the UI, API and docs; ADR 0030 |
| **Soak or fuzz finds something big late** | Start F1 and P3 early (they depend little on the features); run the nightly jobs as soon as they exist |
| **Benchmarks that cannot be compared** | One script, one documented machine, medians of three rounds, nginx as a reference with its configuration published; the doc says what is not comparable |
| **The 1.0 promise freezing a mistake** | L12 promises only what is listed; experimental endpoints can be marked; the review (SR2) and docs (W2, W3) list the surface before the tag |
| **Migrations corrupting a database** | A backup file before every upgrade, one transaction per step, the fresh-equals-migrated test, the upgrade test with real old binaries (PK3) |
| **Scope creep** (WAF, cluster-wide limits, queues, import/export) | Section 2 lists what is out; new ideas go to the ROADMAP's post-1.0 list |
| **Windows differences** (accept behavior, refused connections, timers) | Event-driven waits, the platform rules of AGENTS.md, all three platforms in CI on every PR |

## 11. Touch points with finished work

- **M2:** `max_requests` adds one more eligibility reason beside draining and disabled. Panic mode does not override
  it. The retry budget and replay rules are unchanged, apart from a cut body never being replayable.
- **M3:** connection caps act before the handshake. The existing handshake timeout and concurrency cap stay, and
  HTTP/2 limits stay where they are.
- **M4:** the challenge is answered before the rate limit, so it is never limited. The fuzz targets take
  `eligible_names` and the allowlist parser. The review covers ACME key storage.
- **M5:** limit changes are audited writes. The admin plane's own throttle stays separate, and SR2 decides its
  residual risk behind a reverse proxy. Maintenance answers come before the rate limit.
- **M6:** refusals are 4xx, so `client_errors` sees them at the sampler's capped rate. The unusual-header thresholds
  and the refusal limits are one table (L10). The sampler's token bucket moves to the limits crate. The header named
  by a header-keyed policy is redacted.
- **Schema:** this milestone is the first under the additive-with-migrations rule (C1, S1), and PK3 proves it with
  real released binaries.
